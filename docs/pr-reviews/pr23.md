(internal/engine/messages_sandbox.go) Writable file handle closed without error
handling: in `copyRegularFile`, the `io.Copy` failure path called `out.Close()`
and discarded its error. Closing a writable file can itself report a deferred
write/flush failure, so a real data-loss signal could be hidden behind the copy
error. (github-code-quality[bot], L181)

**fixed**
2a5a5fe. The copy-failure path now captures both errors: if the close also
fails, it returns the copy error wrapped with the close failure; otherwise it
returns the copy error. The success path still returns `out.Close()` directly,
so a deferred write error on success is never swallowed. Propagation-only with
no change to the success behavior the attachment-staging tests already exercise
(`TestStageSendMessage_WithAttachments` et al. copy through this function); the
dual-failure path isn't unit-tested because forcing both `io.Copy` and `Close`
to fail needs dependency injection not otherwise present, which wasn't worth
adding for an error-wrapping change.
