# PR #19 review — feat(filesystem): add reversible move/copy/remove; raise output cap to 32KB

2026-06-21, mode: fix (Copilot review comments)

(internal/engine/mutate_filesystem.go) `trashPathFor` assumes `~/.Trash` exists;
if it's missing (or is a non-directory), staging still succeeds but the later
`mv` fails at execute/undo time. Since staged plans are meant to be executable
as-is, validate the Trash directory exists and is a directory during staging.

**fixed**
`trashPathFor` now stats `~/.Trash` up front and returns a clear error if it is
missing or is not a directory, so the failure surfaces at stage time (where the
caller can react) instead of when the staged `mv` runs. Added
`TestTrashPathFor_MissingTrashDir` (missing dir and file-where-dir-should-be) and
`TestStageRemove_FailsWhenTrashMissing` (the validation surfaces through a real
mutator at stage time).

---

(internal/engine/mutate_filesystem.go) `trashPathFor` only checks for name
collisions at stage time. Because execution/undo can happen later, a new
same-named item may appear in the Trash between stage→execute (remove) or
execute→undo (copy), and `mv` would then overwrite that Trash entry. Consider
making Trash destinations inherently unique per staged plan.

**status**: won't fix (accepted risk)
This server runs as a single user against their own account. For the staged
Trash name to be clobbered, that same user would have to manually create a file
with the exact disambiguated name (e.g. `test 2.txt`) inside `~/.Trash` in the
brief window between staging and execute/undo — vanishingly unlikely in practice.
A token-derived suffix would also make the trashed filename uglier for the common
case with no real-world benefit. We knowingly accept this very small race and
leave the collision logic as-is.
