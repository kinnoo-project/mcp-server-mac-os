(internal/engine/builtins_network.go) The per-trace timeout handling in
`runTraceRoute` was ineffective: when the `runCtx` deadline fired, `runCommand`
returned a non-nil error, so `if err != nil { return "", err }` returned
immediately and the later `if ctx.Err() == nil && runCtx.Err() != nil { ... }`
friendly-timeout branch was never reached — a bounded, expected timeout leaked
out as a hard error instead of the intended partial/timeout message.

**fixed** (b6f7083)
Reordered so the timeout case is recognized **before** the error case (a fired
deadline surfaces as *both* a runCommand error and a set `runCtx.Err()`, so the
error check must not come first). Pulled the rendering into a pure
`classifyTraceResult(host, timeout, res, runErr, parentCancelled, deadlineFired)`
so the precedence is deterministically unit-testable without a live traceroute
that has to actually hang — `TestClassifyTraceResult` covers: deadline-fired with
partial hops (error ignored, message + partial route returned), deadline-fired
with no output, a genuine caller cancellation (NOT massaged into a timeout — real
error surfaced), a plain non-timeout error, clean success, and empty-success. The
helper now also surfaces any partial route gathered before the deadline, which is
more useful for a traceroute than a bare message.

Also applied the same reordering to the pre-existing `runPingHost`, which had the
identical latent bug in its backstop branch (its timeout is a rarely-hit
name-resolution-hang guard, so the dead branch had gone unnoticed).

docs/TESTS.md updated to record `TestClassifyTraceResult` and the shared ping
reordering.
