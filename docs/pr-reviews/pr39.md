# PR #39 review — feat(filesystem): spotlight_search (U4)

2026-07-02, mode: fix (Copilot review)

Copilot approved the change (2 comments, both minor and correct) and its
overview accurately described the operation. Both were addressed in `a0a126e`.

(internal/engine/builtins_spotlight.go) Trim the query once up front and use
the trimmed value for both the required-check and the dash-leading
option-injection guard. As written, leading/trailing whitespace was accepted
and the dash-check ran on the untrimmed string, weakening the "first
character" guarantee for mdfind parsing.

**fixed**
`runSpotlightSearch` now does `query = strings.TrimSpace(query)` immediately
after reading the parameter, and the required-check, the `HasPrefix(query,
"-")` guard, and the mdfind argv all use that trimmed value. This closes the
theoretical bypass where a value like `" -e"` would pass the dash guard (its
first character is a space) yet reach mdfind with a leading dash once
whitespace is disregarded. Added `" -e"` and `"  --"` to
`TestRunSpotlightSearch_RejectsDashLeadingQuery` to lock the behavior in.

---

(internal/engine/builtins_spotlight_test.go) The SAFETY file header claimed the
real `mdfind` invocation uses a "nonsensical query token engineered to match
nothing", but the test actually uses a normal query ("report") and relies on
scoping to an empty temp dir for safety — the header was misleading.

**fixed**
Rewrote the SAFETY header to describe the actual mechanism: the one real
`mdfind` call is scoped to a fresh empty `t.TempDir()`, guaranteed to match
nothing regardless of the machine's Spotlight index (and the header now notes
that an unscoped search would be unreliable and could surface real files,
since this very file contains the query token).
