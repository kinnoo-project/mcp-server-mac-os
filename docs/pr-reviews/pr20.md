# PR #20 review — added reversible copy, move, remove files capabilities to filesystem category

2026-06-21, mode: fix (Copilot review comments)

(internal/engine/mutate_filesystem.go) `resolveFinalDestination` verifies the
final destination does not already exist, but doesn't verify the destination's
*parent directory* exists and is a directory. Since `mv`/`cp` won't create
intermediate directories, staging can succeed while producing a plan guaranteed
to fail at execute/undo time — conflicting with the staging contract used
elsewhere (e.g. `trashPathFor` fails fast when `~/.Trash` is missing).

**fixed**
`resolveFinalDestination` now stats the final destination's parent and returns a
clear error if it is missing or is not a directory, so a doomed move/copy is
refused at stage time rather than failing when the forward command runs. Added
two cases to `TestStageMove_Rejects` (missing parent dir, parent path is a
regular file). Also documented the precondition in the `move`/`copy` manifest
`destination` descriptions and in docs/TESTS.md.

---

(internal/engine/mutate_filesystem.go, stageMove guardrails comment) The comment
says `mv` would parse a dash-leading operand as a flag "despite the `--`
terminator". After `--`, option parsing is normally stopped; the dash rejection
is a policy choice to mirror other mutators, not a `--` limitation. Misleading
for future maintainers.

**fixed**
Reworded the guardrail comment to state plainly that the argv always carries a
`--` terminator (so `mv` already treats a dash-leading value as data) and the
rejection is a deliberate project guardrail that returns a clear "prefix with ./"
error — not a workaround for any `--` limitation.

**fixed**
Reworded `validateExistingOperand`'s comment the same way. For consistency, also
