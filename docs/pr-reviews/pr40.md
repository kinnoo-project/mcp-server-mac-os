(internal/engine/mutate_clipboard.go) `stageWriteClipboard` reads the prior
clipboard text via `runCommand`, which buffers all of pbpaste's stdout in
memory with no cap. Since undo only retains up to `maxClipboardBytes`, a very
large text clipboard causes unnecessary latency/memory use (and is copied again
when converting `priorRes.Stdout` to `[]byte`). Copilot suggested reading
pbpaste stdout with a hard limit of `maxClipboardBytes+1` so oversized prior
contents can be detected without slurping the entire clipboard.

**status**: declined (with reasoning), code comment added

The suggestion is theoretically valid but was **not adopted**, because a
streaming/capped read here would diverge from the engine's established
convention for exactly this situation:

- The directly-analogous case is the pipeline **intermediate-size cap**
  (`pipeline.go:141`): each stage runs to completion buffering its full stdout
  via the shared `runCommandWithStdin`, and the size limit is enforced
  *afterward* with `len(res.Stdout) > maxPipelineStageBytes`. That is the same
  buffer-then-check shape `stageWriteClipboard` uses (`planWriteClipboard`
  declines undo when `len(prior) > maxClipboardBytes`).
- `read_clipboard` — introduced in this same PR, reading the *same* pbpaste
  output — also buffers fully and bounds downstream via `compactOutput`.
  Single-casing only the write probe would make the two clipboard ops
  inconsistent.
- The shared `execCommand` path deliberately centralizes context binding,
  the wall-clock timeout, and error handling; a bespoke capped-exec for one
  probe would duplicate that machinery.
- Functionally the result is already correct: an oversized prior clipboard
  yields `Inverse == nil` (no undo offered). The only cost is transiently
  buffering an unusually large text clipboard before discarding it — a
  pathological case, since the value is whatever a user manually copied.

A streaming capped-exec helper would be a sensible **cross-cutting** improvement
(it would benefit every read in the engine, not just this probe), but it is out
of scope for this PR. To keep the choice from being re-raised, a code comment
was added at the probe explaining why buffer-then-check is deliberate and
consistent with the pipeline cap and `read_clipboard`.
