# PR #50 — U15: `display_sleep` + `wifi_set_power` — Copilot review writeup

**Branch:** `feat/display-sleep-wifi-power` → `build`
**Copilot review:** COMMENTED, 1 inline comment (a non-bug robustness refinement).

## The comment

**`internal/engine/mutate_system_power.go` — `stageWifiSetPower`: check the exit
code of `networksetup -listallhardwareports`.**

`runCommand` reports a non-zero exit through `ports.ExitCode`, not through `err`
(a subprocess that starts and exits non-zero is not a Go-level error). The
original code checked only `err` after the hardware-port listing, so a genuine
failure of that command — which would leave `ports.Stdout` empty — fell through
to `parseWifiDevice` returning `""` and was reported as "no Wi-Fi interface was
found on this Mac", masking the real cause and making staging/debugging harder.

**Assessment:** valid. Not a security or correctness-of-the-happy-path defect
(the toggle still works when the machine is healthy), but a real
error-transparency regression, and an *internal inconsistency*: my own
`probeWifiPower`, a few lines below, already checks `ExitCode` and surfaces
stderr. The listing call should do the same.

**Fix (`44e28ea`):** after the `-listallhardwareports` call, if
`ports.ExitCode != 0` return an error carrying the exit code and trimmed stderr,
before `parseWifiDevice`. Now a real listing failure reports its actual cause;
the "no Wi-Fi interface" message is reserved for the genuine case of a healthy
run that simply has no Wi-Fi port (e.g. a Mac with only Ethernet).

**Why no new unit test:** the branch fires only on a live non-zero exit from
`networksetup`, and `runCommand`/`execCommand` invoke the real binary with no
injection seam to force a failure — the same reason `probeWifiPower`'s pre-existing
`ExitCode` branch is not unit-tested. The change is a small defensive guard
mirroring an already-shipped pattern.

## Note on the sibling read path

`runWifiStatus` (`builtins_system.go`) has the same "check err but not ExitCode
on `-listallhardwareports`" shape. It is pre-existing and out of scope for this
PR, and its blast radius is identical (a misleading "no Wi-Fi interface"), so it
is left as-is rather than swept into this change; worth a follow-up if we want the
read path to report listing failures as transparently as the new mutator now does.
