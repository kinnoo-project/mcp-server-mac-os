# PR #44 review — feat(filesystem): compress + extract via bsdtar (U9)

2026-07-02, mode: fix

Copilot submitted a COMMENTED review with three inline comments — two flagging
the same real inaccuracy in user-facing wording, one a test-hygiene point.
Neither was a logic bug (the mutators, guardrails, and zip-slip behavior were
correct), but all three were accepted and addressed in commit `0e80019`.

---

(internal/engine/mutate_filesystem.go:672) The extract **preview** claimed
members with "an absolute or '..' path are refused." That overstates the
guarantee for absolute members: bsdtar's secure default (no `-P`) *refuses* a
`..` member outright but *strips the leading `/`* from an absolute member so it
lands harmlessly INSIDE the destination. The code comment on `stageExtract` and
`TestStageExtract_RefusesZipSlip` already described this correctly — only the
preview was wrong.

**fixed**
Reworded the preview to state each mechanism separately: "a member with a '..'
path is refused, and an absolute member has its leading '/' stripped so it lands
inside." The security conclusion (nothing escapes the destination) is unchanged;
the wording now matches the actual behavior.

---

(internal/registry/manifests/filesystem.json:622) The extract **manifest
summary** — the model-facing description — carried the same inaccurate "absolute
members are refused" guarantee.

**fixed**
Same rewording applied to the summary, so the operation the model reads about no
longer promises an incorrect security property.

---

(internal/engine/mutate_filesystem_test.go:948) `TestStageExtract_RefusesZipSlip`
called `os.Remove("/tmp/abs_evil.txt")` inside its failure branch. If the test
ever failed, that would delete a path OUTSIDE the test's own temp directory —
and an unrelated pre-existing file at that fixed path would be removed too. A
test should never delete outside its sandbox.

**fixed**
Dropped the `os.Remove`; the branch now only asserts and fails (with a clearer
message explaining the expected de-slash behavior). Since bsdtar strips the
leading `/`, the file is never written to `/tmp` in the passing case, so there is
nothing to clean up — and a failing run leaves the escaped artifact in place for
inspection rather than silently deleting a real file.
