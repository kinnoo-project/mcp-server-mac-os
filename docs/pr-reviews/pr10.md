# PR #10 review — Add application-messages capability: read + search + send iMessage

2026-06-19, mode: fix

Three Copilot comments, all correct and addressed.

---

(internal/engine/builtins_messages.go) The SQL-injection safety comment says
escapeSQLLiteral works by doubling a right-double-quote character (`”`); it
should refer to doubling single quotes (`'`) for SQLite string literals.

**fixed**
The comment had a curly `”` where it meant a single quote — a smart-quote
artifact from writing two consecutive single quotes in prose (the same
characters auto-convert on edit). Reworded to "doubles each embedded
single-quote character", which avoids the sequence entirely. Verified the file
now contains no smart-quote characters. NB: the actual code was never affected —
`escapeSQLLiteral` uses a literal `"''"` (straight quotes), confirmed by byte
inspection and by `TestEscapeSQLLiteral`; only the doc comment was wrong.

---

(internal/engine/builtins_messages.go) search_messages used SQLite `LIKE`
without escaping LIKE metacharacters, so a query containing `%` or `_` became a
wildcard match rather than the literal substring the param promises.

**fixed**
Switched the predicate to `instr(lower(m.text), lower('<esc>')) > 0`, a literal
case-insensitive substring match (matching the previous ASCII case-insensitive
behavior of LIKE) that treats `%`/`_` as ordinary characters. The term is still
embedded only as the escaped SQL literal. Validated against the real chat.db
(counts only): `instr(... '%')` now matches the 147 messages that literally
contain a percent sign, where the old LIKE would have matched everything.

(Out of scope, noted for a follow-up: search only scans the `text` column, so
messages whose text lives solely in `attributedBody` aren't searched — a broader
change than this comment.)

**fixed**
