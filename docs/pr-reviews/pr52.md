Copilot reviewed 14/14 files and left **2 inline comments**, both on
`internal/engine/builtins_appstore.go`. Neither was a bug; both were robustness
refinements that strengthen the exact "scheme/host/path are Go-side constants"
guarantee `search_app_store` rests on, so both were applied.

## Comment 1 — `http.DefaultClient` follows redirects (line 105)

> `http.DefaultClient` follows redirects by default … a compromised/misbehaving
> endpoint could redirect the request to a different host, which undermines the
> "fixed scheme/host/path" guarantee. Consider disabling redirects …

**Applied.** The request now goes through a dedicated `appStoreHTTPClient` whose
`CheckRedirect` returns an error, so **no redirect is ever followed**. The
endpoint is a fixed Apple host that answers 200 with JSON — a 3xx is never
legitimate here, and following one would silently send a follow-up request to a
different origin, defeating the guarantee. Refusing surfaces as a clear error.

Regression: `TestRunSearchAppStore_RefusesRedirect` stands up a redirector and a
target httptest server and asserts the target is **never contacted**.

## Comment 2 — silent truncation past the 1 MiB cap (line 114)

> The response-size cap uses `io.LimitReader` but doesn't detect truncation. If
> the App Store ever returns >1 MiB, the body will be silently truncated and then
> `json.Unmarshal` will fail with a confusing parse error. Consider reading up to
> `max+1` bytes and returning a clear "response too large" error …

**Applied.** The body is now read with `io.LimitReader(resp.Body, cap+1)` and an
explicit `len(body) > cap` check returns a clear
`"the App Store response exceeded the N-byte limit"` error instead of truncating
into a confusing parse failure. `appStoreMaxResponseBytes` was changed from a
`const` to a `var` so a test can lower it.

Regression: `TestRunSearchAppStore_RejectsOversizeResponse` lowers the cap and
asserts the over-limit path returns the "exceeded" error.
