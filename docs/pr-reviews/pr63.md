## Comments and resolutions

### 1. `runCredentialLookup` masks real failures as "not found" + a grammar slip (builtins_keychain.go:173) — FIXED
Copilot noted that treating *any* non-zero exit from `security find-*-password` as
the benign "no match" case is correct for the common exit-44 `errSecItemNotFound`
outcome but would also swallow *other* failures — a usage error, a
permission/interaction error, an unexpected non-zero exit — reporting them as
"No … was found". For a keychain lookup that is the dangerous direction: a denied
read would be misreported as "you have no such saved item". It also flagged that
the message rendered ungrammatically ("No **a saved password** was found") because
the `label` carried its own article.

Fix — the same shape as the V5 `interpretQuarantineResult` refinement:
- Extracted the branching into a pure, unit-tested `interpretCredentialResult(kind, res)`
  that distinguishes **three** cases instead of two:
  - **match** (exit 0) → parse the attribute dump through the `keychainMetadata`
    allowlist (secret-safe as before);
  - **genuine not-found** (`ExitCode == 44`, or stderr contains "could not be
    found") → the plain "No … was found matching that search." answer;
  - **any other failure** → returns an *error* carrying `security`'s stderr, never
    a false "not found".
- Reworked the `kind` argument to a bare noun phrase ("saved password" / "saved
  internet login") so the messages supply their own article: "Found **a** saved
  password …" and "**No** saved password was found …" now both read correctly.

Confirmed against the real `/usr/bin/security` (the `MCP_SECURITY_LIVE=1` gated
test still passes). Covered by the new `TestInterpretCredentialResult`
(match / not-found-44 / other-failure branches), which also pins the exact
not-found wording so the "No a …" slip can't reappear.
