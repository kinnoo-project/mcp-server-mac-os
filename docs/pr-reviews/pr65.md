## Comments and resolutions

### 1. `validateShortcutName` under-rejects control chars and returns untrimmed input (mutate_shortcuts.go:71) — FIXED
Copilot noted the guard claimed to reject "control" values but only blocked
NUL/LF/CR, and returned the input untrimmed. Two concrete consequences:

- **Other ASCII control bytes** (tab, ESC, DEL) could pass validation and reach
  the forward argv, the stage-time existence probe, and the human-facing preview.
- **Untrimmed return** meant a name with stray leading/trailing whitespace would
  clear validation but then fail the existence check with a confusing "no such
  shortcut", because `listShortcutNames` trims each listed name before comparison.

Both were legitimate. Fix: `validateShortcutName` now trims once and rejects any
ASCII control character (`r < 0x20 || r == 0x7f`), matching the codebase's
existing `validateKeychainQuery` / `rejectControlChars` validators, and returns
the trimmed value so it lines up with the trimmed listing. Empty (including
whitespace-only, which trims to empty) and dash-leading values are still rejected;
internal spaces remain allowed, since users name shortcuts freely.

Test coverage extended: `TestValidateShortcutName_RejectsHostile` now includes
tab/ESC/DEL rejection cases (which the original NUL/LF/CR-only guard would have
let through) and asserts that a padded name is *trimmed* (returned as the trimmed
value) rather than rejected.
