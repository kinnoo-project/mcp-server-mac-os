**issue**
Two capabilities the architecture does not yet provide, flagged for awareness (not defects — deferred scope):

1. **Server-side composition** — ~~a single capability that bundles several binaries into one transactional unit with shared state. This is out of scope for the read-only spine (Slices A–C).~~ **Resolved (2026-06-18):** the `pipeline` tool (`internal/engine/pipeline.go`, `internal/server/pipeline.go`) chains several read-only, binary-backed capabilities, piping each stage's raw stdout into the next stage's stdin — a real server-side pipe, no shell, no model-mediated data passing. Deliberately scoped to read-only stages only (see point 2's resolution below for why), sequential/buffered rather than a true concurrent OS pipe (see `docs/issues/note-pipeline-design-decisions.md`), capped at 5 stages with a 1 MiB intermediate-output limit. See the [pipeline section](../architecture.md#pipeline-composing-capabilities) of `docs/architecture.md`.

2. **Transactional multi-step mutations with rollback** — ~~the `plan`/`commit` path and the `internal/transaction` (and `internal/snapshot`) machinery were explicitly deferred to the later mutation phase.~~ **Partially resolved (Phase 2, 2026-06-17):** `internal/transaction` now exists (a generic, thread-safe, TTL one-shot token store) and backs a single-step stage → execute → undo flow, proved on `mkdir` and `write_setting`. What remains open is specifically **multi-step *mutation*** rollback: chaining several mutations as one unit with a best-effort + report failure policy (stop on first failure, report what completed, let the user `undo` the completed reversible steps) is still future work — see the Roadmap in `README.md`. This is explicitly NOT solved by item 1's `pipeline` tool, which is read-only-only by design precisely so it never needs rollback; multi-step mutation plans are a distinct, harder problem with their own state-tracking and partial-failure semantics. There is also no `internal/snapshot` package; undo today is value/inverse-command based (e.g. `mkdir` ↔ `rmdir`), not snapshot-based, and that has been sufficient so far.

Nuance that prompted item 1's original write-up: before the `pipeline` tool, step chaining was entirely LLM-driven — the model read one step's text output and formed the next step's arguments, with data passing **through the model's context**. That is still how a model would chain, say, a read-only result into a *mutation's* parameters (mutations are outside `pipeline`'s scope) — only read-only-to-read-only chains get the real server-side pipe now.

**status: item 1 resolved (read-only composition); item 2 partially fixed (single-step mutation), multi-step mutation rollback still open**
