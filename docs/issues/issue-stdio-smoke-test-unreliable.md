**issue**
The first end-to-end check of the stdio server was a shell smoke test that piped a hand-written JSON-RPC handshake (`initialize` / `notifications/initialized` / `tools/list`) into the binary. It produced zero output and looked like a server failure, but the real cause was the test harness: piping closes stdin immediately, and the server tears down on EOF before flushing its responses. A real MCP client keeps the connection open, so the shell test was not representative of actual operation. (This same smoke test is, however, what surfaced the startup panic recorded in `bug-jsonschema-tag-format-panic`.) Encountered during Slice D.

**fixed**
Replaced the brittle shell smoke test with an in-process integration test using the SDK's in-memory transport (`mcp.NewInMemoryTransports`). It connects a genuine MCP client to our server and drives the real protocol: `ListTools` (asserts the single `filesystem` domain tool and its embedded operation menu) and `CallTool` for `filesystem(operation: "pwd")` (asserts a real absolute path comes back). This exercises the same machinery a production client uses, is deterministic, and lives in the repo as a permanent regression test (`internal/server/integration_test.go`).
