     Plan: Network Diagnostics & Info Capability

     Context

     The server today can report Wi-Fi/Bluetooth/power state (the system tool)
     but has no way to answer the everyday network questions a user actually
     asks: what's my IP and router, who else is on this network, can you ping 
     that host, what's resolving DNS, what's listening on my ports? This is
     exactly the "new senses the Bash tool can't safely provide" sweet spot from
     the roadmap (docs/ideas/next-capabilities-20260620.md §6): the value is
     giving the agent safe, parsed reach into the network stack, with the
     dangerous edge — model-controlled hostnames flowing into ping/dig —
     neutralized by strict input validation (CLAUDE.md §4 /
     darwin-execution.md).

     Decided scope (this round is entirely read-only):
     - New top-level network domain tool (auto-registers from a new manifest
     category — confirmed Server.Domains() is registry-derived,
     internal/server/tools.go:130).
     - LAN discovery ships as two ops: passive ARP-cache read and a separate,
     explicitly-chosen active ping-sweep.
     - No set_dns and no Bluetooth toggle — Bluetooth on/off has no first-party
     CLI (blueutil is third-party and outside the trusted dirs /bin /sbin 
     /usr/bin /usr/sbin), so toggling stays a open_settings(pane=bluetooth)
     handoff, which already exists. Therefore no mutation/undo code is needed.
     - Diagnostic prompts ("can't reach the internet", "mouse won't connect")
     are answered by the model composing these primitives, not a dedicated
     bundle. Op summaries are written to make that composition obvious.

     All target binaries exist under trusted dirs (verified): networksetup
     /usr/sbin, scutil /usr/sbin, ping /sbin, dig /usr/bin, ifconfig /sbin,
     route /sbin, arp /usr/sbin, lsof /usr/sbin, system_profiler /usr/sbin. No
     policy change needed (internal/policy/binaries.go allowlists those dirs).

     Architecture fit

     Every new op is a builtin (parses/orchestrates subprocess output in Go,
     returns finished text) following the exact builtins_system.go precedent —
     not generic/named argv builders — because each either parses output or
     validates input. Builtins receive the normalized param map and return a
     string; register in the builtins map (internal/engine/builtins.go:29). No
     os/exec directly: resolve via policy.ResolveBinary and run via runCommand
     (internal/engine/executor.go), which already binds to ctx and applies the
     8KB truncation rule.

     Security crux — host validation (the one piece that must be airtight)

     ping_host and dns_lookup take a model-controlled host. Add a shared helper
     validateNetworkHost(s string) error in builtins_network.go:
     - non-empty, length ≤ 253;
     - reject leading - (option injection) and reject @/+ (dig treats these as
     server/query-option);
     - allowlist charset [A-Za-z0-9.:-] only (covers hostnames, IPv4, IPv6) —
     rejects spaces, /, shell metacharacters, control chars.
     This single allowlist is the guard for both ping and dig (dig has no --
     terminator, so validation — not a terminator — is the defense). Every host
     that passes is safe as a positional/name argument. scan_lan only ever pings
     addresses it computed itself, never model input.
