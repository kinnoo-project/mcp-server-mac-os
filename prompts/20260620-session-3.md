  How /tmp cleanup actually works on macOS

  - /tmp is a symlink to /private/tmp.
  - The cleaner is /usr/libexec/tmp_cleaner, run by a launchd job
  (com.apple.tmp_cleaner) daily at midnight. The old FreeBSD-style
  /etc/periodic/daily/*clean-tmps* + periodic.conf mechanism I'd half-remembered
  is not present on this macOS at all.
  - tmp_cleaner is documented to remove items not touched in ~3 days, but
  empirically it's conservative: this Mac currently has 151 files older than 3 
  days in /tmp, some 11–12 days old. So in practice it leans on disk-space
  pressure rather than a hard 3-day purge.

  Bottom line: files in /tmp aren't reliably long-lived (they can vanish,
  especially under low disk), and just as importantly /tmp is not where anyone
  would think to look for a screenshot. You're right to flag it — it's a poor
  default for something a user wants to keep.

  Can the user specify a location in the same prompt?

  Not today — the path is fully server-generated, a deliberate choice from
  planning to remove the path-injection surface. But that constraint is easy to
  relax safely: the codebase already accepts user paths in mkdir and open_file
  using TypePath (tilde expansion via expandUserPath) plus a dash-leading-prefix
  guard. Reusing that, the model could turn "screenshot my screen and save it 
  to ~/Desktop/login.png" into a validated path.

  The one wrinkle: a user-named path could overwrite an existing file, which is
  a real side effect. To keep capture_screen in the no-confirm read-only lane,
  I'd refuse to overwrite (error, or auto-suffix) so it still only ever creates
  files. Overwriting would otherwise push it into the stage→execute gate.
