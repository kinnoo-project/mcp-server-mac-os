     Plan: open_website — open a web address in a browser

     Context

     Users naturally say "open YouTube", "open gMail", "open CNN.com", sometimes
     "open
     YouTube on Chrome". Today the application domain tool can open an app
     (open_application) or a file (open_file), but there is no operation for
     opening a website in a browser. This adds that missing third member of the
     "open …" family.

     Two decisions, confirmed with the user, shape the design:

     1. The model routes, the server validates. This codebase already exposes
     operations as data and lets the model pick which one to call. So the
     "is YouTube an app, a website, or a file?" judgment stays with the model —
     it
     already knows YouTube is a website and resolves it to youtube.com. The
     server
     does not become a smart dispatcher; it exposes a clean, well-described
     open_website operation and validates hard. (Mirrors how open_application
     and open_file are separate, explicit operations.)
     2. Security: the URL scheme is constrained to http/https. Every existing
     URL-using operation (call, open_settings) builds the URL in Go from
     validated/enumerated input and never hands a raw model URL to open. A
     website
     operation must respect that: a model-supplied address is accepted only
     after we
     confirm its scheme is http/https, so open can never be steered into
     file://, tel:, javascript:, or a custom-scheme handler.

     The user also chose: accept a bare domain OR a full URL (normalize a bare
     domain to https://); and stage for confirmation (route through the execute
     gate like open_file, not auto-commit), with no undo (you can't reliably
     close just the tab that was opened).

     What exists / what to reuse

     - internal/registry/manifests/application.json — the application domain's
     operation catalog. Adding open_website here lengthens the existing
     application tool's menu; no new MCP tool surface (one tool per category,
     per internal/server/tools.go).
     - internal/engine/mutate_apps.go — home of stageOpenApplication /
     stageOpenFile and the shared validateAppNameValue (reused to validate the
     optional browser name: non-empty, no leading dash, no control chars).
     - internal/engine/mutate.go (the mutators map, ~line 96) — register the new
     builder name here.
     - internal/engine/mutate_system.go / mutate_phone.go — reference pattern
     for
     "build the URL/command in Go, Forward: Command{Binary: "open", …},
     irreversible, no inverse."
     - openFileForward in mutate_apps.go — the -- end-of-options convention to
     copy (open -a <app> -- <operand>), so open can never read the address as a
     flag.

     Implementation

     1. Manifest entry — application.json

     Add an open_website operation:
     - binary: "open", builder: "open_website", reversibility: "irreversible",
     risk: "low", no auto_commit (so it routes through stage→execute).
     - params (both arg: { "kind": "none" }, assembled by the builder):
       - url (string, required) — "A website address: a bare domain like
     'youtube.com' or a full 'https://…' URL. Must be a web address
     (http/https);
     not a file path or other scheme."
       - browser (string, optional) — "The browser to open it in, e.g. 'Safari',
     'Google Chrome', 'Firefox'. Omit to use the default browser."
     - summary must steer the model: this is for web addresses, distinct from
     open_application (installed apps) and open_file (local files); staged for
     confirmation.

     2. Builder/mutator — mutate_apps.go

     Add stageOpenWebsite(ctx, cap, in) (*StagedPlan, error):
     - Read url; reject empty.
     - Reject a leading - on the raw input (option-injection guard, same as
     open_file's path check).
     - Normalize + validate in a small pure helper normalizeWebsiteURL(raw)
     (unit-testable, no I/O):
       - If the value has no scheme (no ://), prepend https://.
       - Parse with net/url; require Scheme ∈ {http,https} and a non-empty
     Host. Reject anything else (file:, tel:, javascript:, ftp:,
     custom schemes) with a clear error.
       - Reject control characters / whitespace.
     - Read optional browser; if present, validate via
     validateAppNameValue("open_website", "browser", …).
     - Build the forward command with the -- terminator (copy openFileForward's
     shape):
       - default browser: open -- <url>
       - named browser: open -a <browser> -- <url>
     - Return a StagedPlan with a concrete Preview ("Open https://youtube.com in
     Google Chrome. Proceed?" / "… in your default browser."), Inverse: nil
     (irreversible), routed through the execute gate.
     - Register "open_website": stageOpenWebsite in the mutators map in
     mutate.go.

     3. (Optional, lightweight) fallback nudge

     Enrich the open_application summary in application.json to say it launches
     installed apps and that web addresses use open_website. This keeps routing
     guidance in the model's prompt without coupling operations or adding a
     stage-time
     existence lookup. (No server-side app→website fallback — out of scope.)

     Tests (mutate_apps_test.go, plus injection sweep)

     - Injection regression (mandatory per CLAUDE.md §4.2): feed a flag-like
     url (e.g. "-e foo") and a flag-like browser (e.g. "-FlagName") and assert
     both are rejected (never reach argv as flags). Add open_website to
     injection_sweep_test.go if it enumerates mutators.
     - Scheme rejection: file:///etc/passwd, tel:911, javascript:alert(1),

     - Bare-domain normalization: youtube.com → forward args contain
     https://youtube.com; CNN.com likewise.
     - Full-URL passthrough: https://example.com/path?q=1 preserved unchanged.
     - Named browser: browser: "Google Chrome" → argv ["-a","Google 
     Chrome","--","https://…"].
     - Default browser: omitted → argv ["--","https://…"].
     - Plan shape: Inverse == nil, staged (not auto-commit), sensible Preview.

⏺ Done. Here's what I built and why.

  Answer to your question: was it already implemented?

  Partially. The application tool already had open_application (launch an app)
  and open_file (open a file, optionally in a chosen app), but there was no way 
  to open a website in a browser. I added that as a third operation,
  open_website.

  The key design insight

  In this codebase the model picks the operation — the server just exposes
  clean, well-described operations and validates them. So the "is YouTube an
  app, a website, or a file?" decision is the model's job (it already knows
  YouTube is a website and resolves it to youtube.com). The server shouldn't try
  to be a smart dispatcher that guesses. That's exactly how open_application
  and open_file already coexist, and open_website slots in as the third sibling.
  I also tweaked the open_application description to say it's for installed
  apps and to point web addresses at open_website — a routing hint in the
  prompt, not server-side fallback logic.

  What open_website does

  - Accepts a bare domain or full URL — youtube.com, cnn.com, or https://…. A
  bare domain is upgraded to https://.
  - Optional browser — uses the default browser unless you name one ("open
  YouTube on Chrome" → open -a "Google Chrome" -- https://youtube.com).
  - Staged for confirmation (as you chose), no undo — you can't reliably close
  just the tab that opened.

  The security guardrail that mattered most

  open will launch any scheme it's handed — file:// reads a local file, tel:
  places a call. So a model-supplied address is never trusted: it's validated to
  be http/https only, mirroring how call and open_settings build their URLs in
  Go. One subtle bug I caught and fixed during testing: a scheme-only value like
  tel:911 has no ://, so the naive "default a bare domain to https" path would
  have silently turned it into https://tel:911. The validator now rejects
  non-web schemes before defaulting.

⏺ Done. I addressed the Copilot comment on PR #24, which I agree was correct.

  The comment

  normalizeWebsiteURL had two real bugs in its no-:// branch, both rooted in an
  over-clever heuristic ("if the parsed scheme contains a ., treat it as a
  host:port"):

  1. localhost:8080 was wrongly rejected. A dotless host:port — url.Parse
  reports Scheme="localhost", and the dot-check treated that as a forbidden
  non-web scheme. Common dev URLs failed.
  2. http:example.com was silently mangled. A web scheme missing its // slipped
  past the scheme check and got rewritten into the garbage URL
  https://http:example.com.

  The fix (dec50f4)

  For a no-:// value that carries a scheme prefix, the logic is now explicit:
  - http/https without // → rejected as malformed (no more silent rewrite).
  - Known non-web schemes (tel, sms, mailto, file, ftp, javascript, …) →
  rejected — checked before the port test, so tel:911's all-digit opaque can't
  masquerade as a host:port.
  - All-digit opaque (a port) → accepted as host:port and defaulted to https, so
  localhost:8080, example.com:8080, and 127.0.0.1:3000 now work.
  - Anything else (myapp:foo) → rejected.

  The security guarantee is unchanged: whatever is returned is always an
  http/https URL with a host, so open is only ever handed a web address. I
  extracted validateWebURL and isAllDigits helpers for readability, extended
  TestNormalizeWebsiteURL with the three host:port acceptances and the new
  rejections, and updated the design note and TESTS.md.
