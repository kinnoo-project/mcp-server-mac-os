  Revised plan: fix attachment sends via a sandbox-readable copy (no user setup)

  What we proved

  - Root cause: Messages.app is sandboxed and cannot read attachment files 
  outside its sandbox (/tmp, ~/Downloads) when handed a path via AppleScript →

  This needs zero user setup, no Shortcut, no Accessibility, no committed asset,
  no new trusted binary.

  How it works

  At stage time, stageSendMessage will:
  1. Sweep stale copies — delete …/Data/tmp/mcp-send/* subdirs older than ~1
  hour (bounds disk; the transactional-state "staging directory" pattern).
  2. Copy each validated attachment to
  …/Data/tmp/mcp-send/<uuid>/<originalBasename> (preserves the filename the
  recipient sees).
  3. Build the Forward osascript over the copied paths; the preview still shows
  the original basenames.

  The copy is harmless scratch in the app's own sandbox (nothing is sent until
  execute), and we don't delete the copies in the same op — they must outlive
  the async upload, so the next send's sweep reclaims them. The irreversible
  send still happens only at execute; Inverse stays nil.

  Why copy-at-stage, not execute: the engine runs Forward as one subprocess with
  no Go hook in between, so the readable copy must already exist when Forward
  fires.

  Outcome

  Your hunch was exactly right — copying the file into the Messages store first
  works. It generalizes even better: the file just has to live anywhere inside 
  Messages' sandbox, and the existing AppleScript send then uploads it normally.
  No Shortcut, no Accessibility, no user setup.

  Root cause (confirmed, not theorized)

  Messages.app is sandboxed and can't read attachment files handed to it via
  AppleScript from outside its sandbox (~/Downloads, /tmp). The send silently
  fails to transmit — transfer_state=6, error=3 in chat.db — while text is
  unaffected. Size was never the issue.

  The fix

  At stage time, each attachment is copied into
  ~/Library/Containers/com.apple.MobileSMS/Data/tmp/mcp-send/<id>/<i>/<name>,
  and the send references that readable copy.
  - Copy-at-stage because a staged Forward runs as one subprocess with no
  in-process hook before it fires.
  - Copies outlive the async upload; a 1-hour sweep on the next send reclaims
  them.
  - Same-basename files isolated per-index; original filenames preserved for the
  recipient.
  - The hardcoded com.apple.MobileSMS assumption is documented in three places
  (the messages_sandbox.go file header, the bug note, and the absent-container

  — exactly what you asked for.
