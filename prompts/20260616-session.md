  1. "Capability registry" vs. "curated typed tools"

  Curated typed tools (what you have today). Each operation is hand-written Go:
  a struct with jsonschema tags + a handler + an mcp.AddTool registration +
  tests. To add "move file to Trash," you write all of that again. The schema is
  the contract, and the LLM sees N discrete tools.

  - ✅ Best-possible schemas (the model gets exact typed params), compile-time
  safety, each tool's blast radius is explicit and easy to security-review.
  - ❌ Linear code growth; every capability is bespoke. The tool list balloons —
  and large tool lists measurably degrade an LLM's tool-selection accuracy and
  eat context. You will never cover all of Darwin this way. This is your scaling
  fear, and it's a legitimate one.

  Capability registry (data-driven). You build a small, fixed set of engine
  tools — e.g. list_capabilities, plan_action, commit_action. The actual
  operations live in a registry: a list of declarative manifests (data — Go
  structs in a slice, or embedded YAML) where each entry describes one
  capability:

  name: trash_file
  binary: /bin/mv          # or a native API
  params: { path: {type: path, required: true} }
  reversibility: compensatable   # undo = move back from ~/.Trash
  risk: medium
  inverse: <how to compute the undo op>

  The engine reads the manifest, validates params, builds the argv
  deterministically, scores risk, executes, and journals — all generically.
  Adding a capability = adding a manifest entry (+ maybe a tiny inverse
  function), not a new tool.

  - ✅ MCP surface stays small and stable; cross-cutting concerns (validation,
  risk, rollback, audit) are implemented once; capabilities become inspectable,
  testable, diffable data; you can add ops without touching the engine.
  - ❌ More upfront engine complexity; the schema is one level more indirect
  unless you generate tools from it.

  My recommendation: a hybrid, and it's not a compromise — it's the actual 
  "compiler" architecture you were reaching for. Keep the registry as data, then
  have a thin layer generate the MCP tools (or a few dispatcher tools) from the
  registry at startup. You write a manifest; registration, argv-building,
  risk-scoring, and rollback wiring all happen generically. You get typed-tool
  ergonomics for the LLM and data-driven scaling.

  ▎ The registry is your grammar; the engine is your code generator + runtime. 
  ▎ That is precisely how C relates to assembly — not one function per 
  ▎ instruction, but a grammar plus a generator. Your analogy was right; it just
  ▎ points at the registry, not at more tools.

  And critically: you never needed a tool per prompt. One parameterized
  capability (trash_file) covers infinitely many natural-language phrasings —
  mapping language→intent is the client model's job, not yours.

  The elegant part: reversibility class lives in the manifest (reversibility: 
  reversible | compensatable | irreversible). That's how your Q3 and Q4 unify —
  the engine enforces tiering uniformly by reading a field, instead of you
  re-implementing undo logic per tool.

  2. APFS snapshots — honest answer on size & bloat

  How they work: APFS snapshots are point-in-time, read-only, copy-on-write. At
  creation they cost essentially zero bytes. They grow only as blocks diverge —
  a snapshot "pins" the old version of any block that later changes or gets
  deleted, so it can't be freed. So:

  ▎ A snapshot's real cost = the amount of data changed or deleted since you 
  ▎ took it. Take one, immediately undo a 2 GB deletion, and it cost ~2 GB until
  ▎ you delete the snapshot. Take one and change nothing, it costs ~nothing.

  Will it bloat your disk over time? It depends entirely on which API you use:

  - tmutil localsnapshot (Time Machine local snapshots): auto-managed. macOS
  thins them automatically — typically kept ~24h and purged automatically under 
  disk pressure. These won't bloat indefinitely.
  - Custom named snapshots (fs_snapshot API / mount_apfs): you own the 
  lifecycle. These persist until you delete them and will accumulate if
  untracked.

  So the correct pattern for a rollback engine: create a named snapshot
  bracketing a risky transaction, and delete it on successful commit or after a 
  short TTL. Never accumulate. Treat it as a transaction log that you
  garbage-collect, not a backup archive.

  Two important caveats so you don't over-rely on them:
  - Restore is whole-volume, not granular. Reverting to a snapshot rolls back
  the entire volume (and needs a reboot for the boot volume). For undoing one
  file, that's a sledgehammer.
  - For per-file undo, Trash + a saved inverse op is lighter and more targeted.
  You can mount_apfs a snapshot read-only and copy one file out, but it's
  fiddly.

  The honest synthesis: snapshots are the right backstop for the irreversible / 
  bulk tier (e.g., "delete 4,000 files," "rewrite a config dir") — a cheap,
  Mac-native "oh no" button. For ordinary single-file mutation, copy-to-Trash or
  copy-aside is simpler. This maps cleanly onto your tiering: compensatable ops
  use Trash/inverse; irreversible/bulk ops get wrapped in a snapshot bracket;
  truly irreversible non-FS ops (kill process, network) get escalated
  confirmation and no false promise of rollback.

  snapshot the pre-state at plan/commit time. The cleanest defaults write
  example:

  - name: write_default
    binary: /usr/bin/defaults
    reversibility: reversible
    params:

      key:    { type: string, required: true }
      value:  { type: string, required: true }

        capability: read_default   # another capability!
        params: { domain: $domain, key: $key }
    inverse:                       # materialized into the journal at commit
      when_prior_existed:
        capability: write_default
        params: { domain: $domain, key: $key, value: $prior }
      when_prior_absent:
        capability: delete_default
        params: { domain: $domain, key: $key }

  Three mitigations make Pattern A's round-trip cost mostly disappear:

⏺ Two good questions, and they share one principle: the engine should fail 
  closed and loud — never silently guess, and never fall back to ungated raw 
  execution. The cleanest way to handle both is to make plan_action return a
  small set of structured outcomes beyond plain success/error. The model already
  knows how to react to each.

  A. When a capability isn't available or can't run

  Don't collapse these into one "error" — they have different right responses. A
  small taxonomy:

  Outcome: not_found
  When: No capability matches the intent (not built yet)
  Response: Say so plainly + offer nearest matches (fuzzy). And log the miss
  (see
     below).
  ────────────────────────────────────────
  Outcome: blocked
  When: Capability exists but is disabled by config/policy, or hits a macOS TCC 
    privacy wall (e.g., needs Full Disk Access)
  Response: Actionable reason: "blocked by macOS privacy — grant Full Disk 
  Access
     in System Settings." Distinct from "doesn't exist."
  ────────────────────────────────────────
  Outcome: precondition_failed
  When: Exists, params valid, but runtime state is wrong (file missing,
    permission denied)
  Response: Surface the specific reason at plan time, before any mutation.
  ────────────────────────────────────────
  Outcome: refused
  When: Irreversible beyond your reversibility bar
  Response: Refuse + explain it needs escalation (the future /force path).

  The most important behavior for all of these: a clear, structured "not
  supported / not permitted" signal so the model relays it to the user instead 
  of quietly running the raw command through its Bash tool. That fallback is the
  one thing that would silently defeat your entire guardrail story — so the
  response copy should gently steer away from it.

  The high-leverage idea here: turn not_found into your roadmap. Append every
  unmatched intent to a capability-gaps log (the requested intent + params the
  model tried). The frequency of misses is a perfectly prioritized backlog of
  what to build next — user friction becomes your build order, for free.
  (Power-user stretch, tabled: the engine could even emit a draft YAML manifest
  for the missing capability for you to review and drop in.)

  B. Ambiguity → clarify, and enforce it

  Two layers, because ambiguity shows up in two different places:

  Layer 1 — capability-selection ambiguity (which operation?). Two more
  structured outcomes:
  - ambiguous — multiple capabilities match ("empty the trash" → trash_file?
  delete_under? empty_trash?). Return the candidates; the model asks the user to
  pick.
  - needs_params — the capability is clear but required args are missing or
  under-specified ("delete my downloads" → which files? all? only old?). Return
  what's missing; the model asks.

  Layer 2 — param/scope ambiguity (you picked the op, but how much?). This is
  already handled by the dry-run preview — plan_action shows exactly what would
  be mutated ("would move 412 files, 8.3 GB"), and the model confirms before
  commit_action. The preview is the clarification for scope.

  The design point worth stating explicitly: clarification is enforced by the 
  protocol, not left to the model's good manners. The LLM is good at asking
  clarifying questions in conversation — but for destructive ops you don't want
  to rely on it choosing to. By having the engine return ambiguous /
  needs_params instead of executing a guess, the question becomes structurally
  unavoidable. Belt and suspenders: the model clarifies naturally, and the
  engine refuses to proceed without resolution.
