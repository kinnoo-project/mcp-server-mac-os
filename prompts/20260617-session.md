  Why it looped 12 times

  There is no capability that answers "rank the largest files." Look at what the
  model had to work with:

  - du measures the size of directories (and totals), with an optional depth
  limit. It does not sort, and it does not return a "top N" list.
  - find locates files but reports no sizes.
  - ls can sort by size, but only within one directory — it doesn't descend.

  So when you asked for the top 10 files, the model had no single tool that
  produces a ranked answer. It improvised the only way it could: run du on the
  home directory, look at the subdirectory totals, then drill into each
  subdirectory and run du again, trying to manually walk the tree toward the
  biggest things. That's the 12 calls. Each one is a separate round-trip through
  the model's context, which is exactly the slow, token-hungry behavior you
  saw.

  This is the architecture limitation we already wrote down in
  docs/issues/issue-composition-and-transactional-rollback-limitations.md:
  there's no server-side way to chain or aggregate, so any "combine several
  commands into one answer" task gets simulated by the model looping. For
  read-only browsing that was fine; "top 10 largest files" is the first task
  that makes the gap obvious.

  Is du even the right command?

  For directory sizes — "how much is my Downloads folder using" — yes, du is
  exactly right.

  For "top 10 largest files" — no, not by itself. The classic Unix way to answer
  that is something like:

  find ~ -type f -exec du -h {} + | sort -rh | head -10

  Notice the sort -rh | head — the ranking happens in a pipe, after the data is
  collected. Our design deliberately forbids shell pipes and shell wrappers
  (Axiom 2), and every capability is a single binary invocation. So the one
  idiom that actually answers your question is precisely the shape we can't
  express as a capability today. That's the root cause — not a bad prompt.

  The fix that fits the architecture

  We already have the right mechanism: the builtin builder (the same in-process
  concept pwd uses). I'd add one capability — call it largest_files — backed by

  1. Runs a single subprocess to gather sizes (e.g. du -ak <dir>, one pass over
  the tree),
  2. Parses, sorts, and trims to the top N in Go — replacing the forbidden sort 
  | head pipe with ordinary in-process code,
  3. Returns one clean ranked list.

  Result: one MCP call, one subprocess, no looping, and the ranking work happens

  1. Execute should take a token, not the raw resolved command. This is the
  important one. If the execute tool "takes the output of the domain call as an

  thread-safe registry and returns an opaque token (req_…) plus a human-readable

  What I built: a largest_files capability

  I built the named capability (not the generic pipeline — that's the bigger,
  still-open design). It's an in-process builtin, the same mechanism pwd uses:
  the server answers the question itself in Go instead of launching an external
  program.

  Why a builtin and not find or du:
  - "Biggest files under X" has no single-command answer. The real shell idiom
  is du -a | sort -rn | head — a pipeline, which the project's no-shell rule
  forbids.
  - A raw find returns one line per file (the megabytes of blob paths you saw) —
  the flood that hit the 8 KB truncation.
  - du alone can't do it either: it reports directory totals, so the biggest
  "things" would be directories, not files.

  So the builtin does what the shell pipeline does, but in Go:

  How it works (internal/engine/builtins_filesystem.go):
  1. Walks the directory tree once, looking only at regular files (skips
  directories, symlinks, special files — so the answer is truly "largest
  files").
  2. Keeps only the top N in a bounded min-heap — never more than N entries in
  memory, so it's safe over a huge tree like your whole home directory.
  3. Returns just those N ranked lines, largest first, with human-readable sizes
  (48.8K, 3.0G).

  The ranking that sort | head would do happens in Go, so the output is small by
  construction — for the default top 10 it's ~12 lines, which never gets
  anywhere near the truncation budget. The truncation guardrail stays in place
  untouched; we simply stopped producing a flood.

  Robustness details: unreadable directories (permission denied) are skipped
  rather than aborting the scan, and the footer reports how many were skipped so
  the answer is honest about coverage; the walk honors request cancellation; a
  non-directory target returns a clear error.

  The manifest entry (filesystem.json) declares it as a builtin (no binary, like
  pwd) with two params — dir (default .) and count (default 10, max 100) — and
  its summary explicitly tells the model to use this instead of find for
  "biggest files" questions, so it gets picked for prompts like yours.
