  Feasibility: Phone calling (quick answer)

  Yes, both are feasible, and cleanly within the existing architecture:
  - Raw number: open "tel:+15551234567" — /usr/bin/open is already a trusted
  binary, and the tel: URL makes macOS hand off to FaceTime/iPhone (Continuity).
  One-line, low-complexity.
  - Name from Contacts: a fixed osascript against Contacts.app resolves a name →
  phone number(s), then the same tel: open. Same "fixed AppleScript + name as
  argv data" pattern as send_mail. The only wrinkle is disambiguation (multiple
  matches / multiple numbers), which is a preview-and-confirm step, not a
  blocker. So: feasible, modest effort. I'd treat it as its own small
  application-phone domain later, not part of Calendar.

  How Calendar fits the architecture

  Calendar.app and Reminders.app both expose AppleScript dictionaries, so
  everything routes through the same proven path as send_mail: a fixed, reviewed
  AppleScript constant with every model-supplied value bound as on run argv
  data (never concatenated into the script). osascript is already trusted. Two
  macOS-specific realities to flag:
  - TCC permission prompts: the first event read/write triggers a one-time macOS
  "allow access to Calendar/Reminders" dialog. Expected, but worth a note in
  the docs/issues folder.
  - AppleScript Calendar reads can be slow (querying by date range across many
  calendars). The read/query operation needs a bounded date window and a result
  cap, like search_mail's limit.

  A key insight on your "delete is too much power" worry

  Calendar/Reminder deletes don't have to be irreversible like send_mail was.
  Because staging captures the full event (title, start, end, location, notes)
  before deleting, the inverse command is simply "re-create an event with these
  properties." That makes delete compensatable (restored from captured state,
  same as the Trash pattern for files) and plugs straight into the existing
  execute→undo flow. The restored event won't preserve the original's internal
  ID/recurrence/attendees perfectly, but for the events this server creates and
  for simple events it's a real, working undo. That meaningfully lowers the risk
  of granting delete.

  Brainstorm — other Calendar/Reminders features worth considering

  - Free/busy & conflict check — "am I free Thursday 2–3pm?" Pure read, high
  utility, safe.
  - Find next free slot — "find me 30 min tomorrow afternoon." Read-only
  computation over events.
  - Complete a reminder (mark done) — distinct from delete; reversible
  (un-complete).
  - Snooze/reschedule reminder — really just a modify, but worth naming as
  intent.
  - Add invitees/attendees to an event — possible via AppleScript but adds
  complexity (sends invites = irreversible-ish); defer.
  - Recurring events — AppleScript supports recurrence ICS strings; powerful but
  fiddly. Defer to v2.
  - List calendars — trivial read; lets the model target the right calendar
  ("Work" vs "Personal") instead of guessing.
  - Today/agenda summary — convenience wrapper over query with a fixed "today"
  window.

  My recommended v1 cut: list_calendars, query_events (date-range read),
  add_event, modify_event, add_reminder, modify_reminder, plus delete/complete
  depending on your answers below. Free/busy and find-free-slot are strong
  fast-follows.

  Decisions locked in

  Architecture fit (no new subsystems)

  Everything reuses the spine that already runs send_mail: declarative JSON
  manifests → engine validation → osascript with fixed, reviewed AppleScript

  builtins (like search_mail); writes use mutators (like stageSendMail). No
  changes to policy, transaction, or the MCP adapter contract.

  query_events, add_event, modify_event, delete_event.

  add_reminder, modify_reminder, complete_reminder, delete_reminder.
  - internal/engine/builtins_calendar.go — read builtins (list_calendars,
  query_events, list_reminders), each with a fixed query AppleScript, a bounded 
  date window + result cap, and tab-delimited output parsed in Go (mirrors
  parseMdlsOutput).

  builtins_mail_test.go).

  Wiring (one-line edits each)

  mutate.go's mutators map.
  - No server/policy edits — new categories auto-surface as domain tools via
  Domains(); osascript is already trusted.

  Key behaviors

  - Inverse commands (undo): add_* → delete the created item; delete_* →
  re-create from captured properties; modify_* → restore the prior values probed
  at stage time. Each captured before the change, baked into the staged plan.
  - Previews show the verbatim event/reminder fields and spell out exactly what
  undo will do — same discipline as the email preview.
  - Input guardrails: dates/times parsed into a strict typed format (reject
  free-form), calendar/list name validated against list_calendars output, result
  caps on all reads.

  Date/time handling

  A small typed scheme — date (YYYY-MM-DD) and time (HH:MM, 24h) params,
  validated and recombined in Go, never passed as a raw string AppleScript must
  interpret. End-time must be after start-time; this is the main new validation
