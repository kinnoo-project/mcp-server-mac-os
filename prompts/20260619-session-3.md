⏺ The plan is ready. Here's the shape of it:

  The one framework change is an auto-commit execution lane: today every
  mutation is forced through the stage→execute→undo token dance, which is too
  heavy for "open Notes." A capability can now declare auto_commit (data-driven,
  validated to only-low-risk mutations) so it runs immediately and still hands
  back an undo token when reversible. Printing and destructive ops stay staged.

  Four areas, all on the existing manifest+engine spine:
  - application — list/search installed apps (mdfind), list running (osascript),
  open & focus (auto-commit; open probes whether the app was already running so
  its undo=quit is a true inverse), quit (staged).
  - printer (your #1) — list printers + state + jobs (lpstat), print a file /
  generated test page (lp, staged since paper is irreversible). macOS ships no
  CUPS test page, so I embed a tiny one.
  - system — read-only Wi-Fi / Bluetooth / battery+Low-Power status, plus a
  version-aware open_settings that opens the right pane (printers, wifi,
  bluetooth, battery, accessibility…).
  - preferences — extend the existing curated allowlist with accessibility
  toggles (reduce motion/transparency, increase contrast).

  Two constraints baked in throughout: the sudo wall (printer connect,
  power/Bluetooth/Wi-Fi toggles need admin → we surface reads and route the user
  into the right Settings pane), and macOS 11 Big Sur–onward compatibility —
  notably the Settings URL scheme changed in Ventura, so open_settings picks the
  URL by OS version with a top-level fallback. No internal/policy change is
  needed since the trust boundary is directory-based and every binary already
  lives in /usr/bin or /usr/sbin.

  I've also folded in the docs work you asked for (refining the PROJECT_SUMMARY
  Vision to the command-center framing, plus the cross-version compatibility
  note) and a suggested incremental landing order.

     Plan: System-Control & Application capabilities (the "command center" 
     iteration)

     Context

     The MCP server already covers files, preferences, mail, calendar,
     reminders, phone, and
     messages on the capability-registry + engine spine. The next direction
     (Jerry's framing) is to
     make an MCP client connected to this server the command center for daily 
     macOS tasks:
     launch/focus apps, manage printers (his #1 ask: list, print a test page,
     reconnect), adjust
     accessibility, and check Wi‑Fi/Bluetooth/battery — guiding the user into
     the right Settings pane
     where an action genuinely needs admin rights.

     Three constraints shape every choice below:
     - The sudo wall. lpadmin/cupsenable (add/re-enable a printer), pmset -a 
     lowpowermode,
     and Bluetooth/Wi‑Fi power toggles all require administrator rights. sudo
     cannot work over the
     non-interactive stdio transport, so those writes are out. We expose the
     reads and, for the
     writes, open the relevant System Settings pane so the user finishes the
     click.
     - Minimum supported OS raised to macOS 13 Ventura (Darwin 22). Jerry
     decided not to carry
     backward compatibility with older releases. This simplifies the Settings
     opener: Ventura
     re-architected System Settings (new x-apple.systempreferences: pane
     identifiers), and since we
     no longer support Big Sur–Monterey we use only the Ventura+ identifiers —
     no OS-version
     detection, no dual mapping. The old Big Sur (Darwin 20.1.0) baseline in
     PROJECT_SUMMARY.md §2
     and CLAUDE.md §6 must be updated to Ventura 13 / Darwin 22 as part of this
     work.
     - The policy trust boundary is directory-based. Every binary we need
     (lpstat, lp,
     networksetup, pmset, system_profiler, mdfind, open, osascript, lsappinfo,
     sw_vers) already lives in /usr/bin or /usr/sbin, so no internal/policy 
     change is
     needed. osascript calls go through the existing hardened ---terminated path
     (internal/engine/applescript.go); mdfind needs dash-leading-value
     rejection.

     Decisions confirmed with Jerry: (1) add an auto-commit execution lane for
     benign side-effects;
     (2) guided Settings-pane fallback for admin-gated actions (Ventura+ pane
     IDs only); (3) build
     all four areas — Applications, Printers, Accessibility/prefs, System status
     reads;
     (4) raise the minimum OS to macOS 13 Ventura, dropping older-OS backward
     compatibility.

     ---
     Part A — Framework change: the auto-commit execution lane

     Today the server has exactly two lanes: read-only runs immediately;
     everything mutating is
     staged behind an execute token. "Open Notes" should not need a token dance.
     Add a third,
     data-driven lane: a mutation may declare itself auto-commit — it runs
     immediately and, when
     reversible, hands back an undo_token (no staging gate).

     - internal/registry/types.go: add AutoCommit bool 
     \json:"auto_commit,omitempty"`toCapability, with a doc comment: only valid 
     on a mutating (non-read_only) capability whose risk is none/low`; printing
     and destructive ops must stay staged.
     - internal/registry/registry.go (validate): reject auto_commit:true when
     Reversibility == ReadOnly or when Risk is medium/high. Keeps the
     gate-bypass narrow and
     reviewable.
     - internal/server/tools.go (runDomainOperation): new branch order —
     ReadOnly → Run; mutating && AutoCommit → autoCommitMutation; else
     stageMutation (unchanged).
     Add autoCommitMutation: call eng.Stage (computes Forward + Inverse via the
     existing mutator),
     immediately eng.RunCommand(plan.Forward), and if plan.Inverse != nil
     register an undo token
     exactly as Execute does. Reuses all existing engine machinery — no engine
     change.
     - internal/server/menu.go (domainToolDescription): annotate each op's line
     with its lane —
     "runs immediately; reversible via undo", "runs immediately", or "STAGED —
     confirm then execute" —
     derived from Reversibility/AutoCommit so the model knows what a call will
     do.
     - Tests: extend internal/server/tools_test.go / integration_test.go with an
     auto-commit op that
     asserts it runs without a token and returns an undo token; registry_test.go
     for the new
     validation rejections.
